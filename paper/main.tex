\begin{abstract}
	LLMs show promise for software vulnerability detection (SVD). However, their effectiveness in security -critical tasks remains poorly understood. This paper introduces LLMKernelBench, a comprehensive benchmark framework for evaluating LLM capabilities in SVD and patch verification (PV) using real-world Linux kernel vulnerabilities. Our framework includes two complementary datasets—a Primary Benchmark Dataset (PBD) with 314 vulnerabilities spanning 74 CWE types and a Leakage-Free Dataset (LFD) with 103 recent vulnerabilities spanning 19 CWE types to address data contamination concerns. Through systematic evaluation of six state-of-the-art LLMs (three code-specialized, three general-purpose), we reveal critical insights: (1) all models achieve surprisingly low CWE detection accuracy (best: 11.4\% Top-5), with systematic bias toward memory-safety vulnerabilities while completely failing on cryptographic and configuration flaws; (2) models exhibit unexpected reverse bias, detecting patched code better than vulnerable code (average 13.5\% gap), contradicting security-first assumptions; (3) providing explicit CVE/CWE context often degrades rather than improves performance, revealing fundamental reasoning limitations; and (4) increasing code abstraction does not universally hinder detection—some models actually improve with additional context. These findings expose fundamental gaps in LLMs' security reasoning and establish LLMKernelBench as a rigorous foundation for advancing LLM-based vulnerability detection research.
\end{abstract}

\section{Introduction}

% Context, Importance, Introduction, and potential of LLMs in SVD and motivations
LLMs, such as OpenAI's Codex \cite{chen2021evaluating}, Meta's Llama \cite{touvron2023llama, dubey2024llama}, CodeBERT \cite{feng2020codebert}, DeepMind's AlphaCode \cite{li2022competition}, Salesforce's CodeGen \cite{nijkamp2022codegen} and CodeT5 \cite{wang2021codet5}, and PLBART \cite{ahmad2021unified}, have shown remarkable capabilities in understanding programming languages \cite{nam2024using}. These models have potential for assisting developers by providing code suggestions, test generation \cite{alshahwan2024automated, wang2024software, schafer2023empirical}, code documentation \cite{khan2022automatic}, and automating various coding tasks. In fact, by employing advanced methods to train billions of parameters on data from large datasets \cite{hoffmann2022trainingcomputeoptimallargelanguage, gholami2024improvedgeneralizationboundscommunication, digest, thomas2022dynamic}, LLMs demonstrate significant capabilities in various areas \cite{fan2023large}. These models show also great potential for automating SVD, making software more secure by improving efficiency, accuracy, and coverage in identifying and fixing vulnerabilities.

The number of identified and patched software vulnerabilities has surged in recent years, with over 29,000 Common Vulnerabilities and Exposures (CVEs) addressed in 2023, up from 25,084 in 2022 and 20,153 in 2021 \cite{cvedetails2024}. This trend underscores the need for automated SVD to keep up with rapidly evolving digital technologies.
There are, however, several limitations and challenges in SVD from the perspective of both LLMs and traditional VD techniques, such as automatic program repair, fuzzing, and static analysis tools.

From the perspective of LLMs, one major challenge lies in understanding the inherent complexity of vulnerability patterns, which involve intricate interactions between multiple functions or modules within the entire system, rather than isolated code snippets. For instance, a vulnerability might only surface when a specific sequence of function calls is made, or when data flows through various parts of the code in a particular order. Detecting these interactions requires a deep understanding the different parts of the code and of their interdependencies.

A key problem with state-of-the-art LLMs is that they are trained on billions of lines of code without explicitly distinguishing between vulnerable and non-vulnerable code, which can lead to ineffective identification and prevention of software vulnerabilities. For instance, while many LLMs may be trained on data including the Linux kernel project and know the entire codebase, they lack awareness of previous versions of the Linux kernel that contained numerous vulnerabilities. Furthermore, from a software engineering perspective, it is crucial that these models can detect vulnerabilities in code that they have never seen before, such as new projects or entirely new codebases. To enhance their effectiveness in SVD, a dataset that differentiates between vulnerable code versions and their patched counterparts is necessary.

Traditional VD techniques also present significant challenges. APR faces issues with patch quality and generalization \cite{huang2023survey, zhang2023survey}. Fuzzing struggles with achieving comprehensive coverage and detecting logic errors \cite{manes2019art, klees2018evaluating}. Similarly, SATs often suffer from a high rate of false positives and difficulty in understanding dynamic behaviors \cite{pereira2021machine}. These limitations highlight the need for development of more sophisticated approaches, including  effectively leveraging LLMs for SVD, which in turn requires a better understanding of their performance.

% Need for Benchmarking
Despite the potential of LLMs for vulnerability tasks, significant gaps exist in evaluation frameworks for SVD capabilities. Current datasets suffer from a pronounced imbalance wherein vulnerable code blocks are substantially outnumbered by non-vulnerable segments, resulting in skewed performance metrics that fail to accurately represent model effectiveness \cite{gao2023far}. Additionally, many evaluations are conducted in artificially constrained settings using synthetic code snippets, rather than real-world codebases. This restricts the realism and generalizability of the results, whereas incorporating diverse, real-world code would better reflect LLM performance in practical scenarios \cite{chakraborty2021deep, wu2023effective}. 

% Purpose and Objective of the Study
We propose LLMKernelBench, a comprehensive benchmark framework to systematically evaluate pre-trained LLMs' capabilities in SVD and patch verification (PV). Our framework assesses six state-of-the-art pre-trained LLMs using two carefully curated datasets comprising 417 real-world Linux kernel vulnerabilities across 74 CWE types. We focus on Linux kernel C code for its rich vulnerability history and central role in production systems. As the largest open‑source project (~30M LOC) powering Android, servers, and embedded devices, the kernel exhibits diverse, high‑impact flaws. If models cannot generalize to it, they are unlikely to be ready for real‑world deployment. Unlike training-focused datasets, LLMKernelBench prioritizes evaluation rigor by pairing vulnerable code with corresponding patches and addressing data contamination through a leakage-free subset. Our evaluation spans multiple detection scenarios: CWE ranking to assess security knowledge breadth, binary vulnerability identification to test fundamental detection capabilities, and targeted detection with explicit CVE/CWE context to examine reasoning depth.

% Research Questions
\textbf{Research Questions.} We study the following questions:

\begin{itemize}
\item \textbf{RQ1: Binary VD/PV performance} — How well do LLMs classify vulnerable vs. patched code across non‑targeted and targeted settings?
\item \textbf{RQ2: Per‑CWE performance} — Which CWE categories (and pillars) are detected or missed, and how consistent are models across CWEs?
\item \textbf{RQ3: CWE ranking quality} — What is overall ranking accuracy (micro/macro, Top‑$k$) and ranking quality (MRR, HPS)?
\item \textbf{RQ4: Robustness and context} — How do code abstraction levels (function/file/multi‑file) and dataset shift (PBD→LFD) affect performance and generalization?
\end{itemize}

\textbf{Contributions.} This work offers:
\begin{itemize}
\item \textbf{Quality‑controlled kernel benchmark:} PBD/LFD with paired vulnerable–patched code, clean CWE labels (variant and pillar), commit metadata, and a leakage‑free subset (2025 CVEs).
\item \textbf{Unified evaluation protocol:} CWE ranking (Top‑$k$, MRR, HPS) and binary VD/PV (with abstention), analyzed with micro/macro accuracy.
\item \textbf{Comprehensive study of six LLMs:} Results across per‑CWE categories, misclassification patterns, vulnerable vs. patched bias, and PBD→LFD generalization.
\item \textbf{Actionable insights:} Limitations and guidance for deploying LLMs in security triage and for designing future security‑aware benchmarks.
\end{itemize}

\section{Background and Related Work}
\label{section:related_work}

\textbf{CWE Taxonomy Primer.}
The CWE system, developed by MITRE \cite{mitre_cwe}, provides a hierarchical taxonomy of software security weaknesses organized into four abstraction levels: Pillars (highest-level categories like CWE-664: Resource Control), Classes (broader weakness categories), Base weaknesses (specific vulnerability types), and Variants (implementation-specific manifestations). This hierarchical structure enables graduated assessment of security knowledge, where identifying a parent category (e.g., CWE-119: Memory Buffer Bounds) demonstrates partial understanding even when the specific variant (e.g., CWE-120: Buffer Copy) is misidentified.

\textbf{Data Collection.}
Much prior work labels at the file level rather than the function level, which easily introduces errors and bias. REVEAL \cite{chakraborty2021deep}, PatchDB \cite{wang2021patchdb}, D2A \cite{zheng2021d2a}, and MegaVul \cite{ni2024megavul} include every function from a file touched by a vulnerability-related commit, so functions the patch never changed are labeled non‑vulnerable. This creates label noise \cite{iannone2022secret,croft2023data}, duplication/near‑duplication across versions, and strong class imbalance \cite{gao2023far}. Even function‑level datasets (Devign \cite{zhou2019devign}, BigVul, CVEfixes \cite{bhandari2021cvefixes}) often do not strictly pair the exact before/after function bodies and commonly pull commits dominated by refactoring, tests, or configuration updates—changes that are not security fixes (i.e., “noise”). Broad, multi‑project corpora (e.g., BigVul, PrimeVul) favor coverage over precision, which increases noise and duplicates and makes it harder for models to learn the real difference between vulnerable and patched code.

\textbf{Benchmarking LLMs for VD.} Table~\ref{tab:bench-compare} overviews representative efforts. CodeXGLUE/Devign \cite{lu2021codexglue, zhou2019devign} is large but lacks patches and CWE labels. SecurityEval \cite{siddiq2022securityeval} offers only 130 Python snippet pairs without contamination control. VulDetectBench \cite{liu2024vuldetectbench} evaluates program-level C/C++ with 48 CWE inference but no leakage checks. UniVul/LLM4Vuln \cite{sun2024llm4vuln} provides multi-language function pairs with CWE summaries and only partial cutoff awareness. The 5K study \cite{khare2025understanding} aggregates across datasets (partial PV, CWE-wise analysis), while SecLLMHolmes \cite{ullah2024llms} probes robustness on 8 CWEs with contamination tests. Earlier works such as Ullah et al. \cite{ullah2024llms} rely on synthetic/curated cases with limited CWE breadth, and Khare et al. \cite{khare2023understanding} focus on isolated functions—both miss cross-component context and realistic patch effects.

In contrast, LLMKernelBench targets kernel-style vulnerabilities with quality over breadth (Table~\ref{tab:bench-compare}): 314+103 real CVE-linked samples across 74 CWEs; paired vulnerable–patched code (function plus non-functional context); CWE-aware evaluation at variant and pillar levels; and a leakage-free subset using post-cutoff 2025 CVEs. Our commit-level extraction retains only line-modified functions and associated context, avoiding label noise from untouched code. PBD/LFD are designed as stress-test benchmarks that complement rather than replace broader multi-project corpora, which are more suitable for LLM training and fine-tuning.

\section{Benchmarking Approach}
\label{section:approach}
In this section, we present our framework and methodology to evaluate the performance of LLMs in SVD and PV. We start by introducing LLMKernelBench framework in Section \ref{section:framework}. Section \ref{section:dataset} details our dataset construction process. Section \ref{section:metrics} defines metrics for measuring effectiveness in SVD and PV tasks. Finally, Section \ref{section:prompts} presents our standardized prompt templates.


\subsection{LLMKernelBench}
\label{section:framework}
LLMKernelBench is designed to assess pre-trained LLMs (see Table~\ref{table:llm-specs} for the models evaluated) on SVD and PV tasks, focusing on C code from the Linux kernel while being extensible to other programming languages. As illustrated in Figure \ref{figure:framework}, the framework is based on vulnerability metadata and code pairs extracted from Linux CVE commits, and includes prompts designed for SVD and PV tasks. For detection, LLMKernelBench evaluates models in zero-shot settings on both vulnerability identification and PV using binary classification metrics (precision, recall, accuracy, F1) and ranking metrics. This approach ensures benchmark reliability through representativeness (diverse real-world vulnerabilities), adaptability (extendable methodology), portability (applicable across various LLMs), and fairness (standardized evaluation procedures).

\subsection{Dataset}
\label{section:dataset}
Our method systematically extracts pairs of vulnerable code blocks and their corresponding patched versions from real-world Linux kernel commits. We focus on the Linux kernel due to its rich vulnerability history and critical security importance. We collect commit hashes, CVE identifiers, and CWE classifications from well-known vulnerability databases including NVD \cite{nvd2025}, similar to established practices \cite{pereira2022software}. For each vulnerability-fixing commit, we retrieve the vulnerable code from its parent commit (pre-fix version) and the patched code from the commit itself (post-fix version).

Our extraction process identifies all security-related functions and non-functional elements (global variables, macros, type definitions, structs/unions, headers) that were directly modified in each commit. We include only functions with actual line-level changes, excluding unchanged code to avoid label noise. Non-functional elements are tracked separately as they often form critical vulnerability contexts that influence execution across multiple functions. This comprehensive approach assembles cohesive vulnerable and patched code blocks at multiple abstraction levels (single function, multiple functions, multiple files), enabling LLMs to analyze complete contextual information rather than isolated fragments. Table~\ref{table:dataset-stats} summarizes the overall size and composition of PBD and LFD.


\textbf{Manual Review, Denoising, and Deduplication.} Initially, we collected 400 samples for PBD and 110 samples for LFD through our automated extraction process. To ensure dataset integrity and label fidelity, both datasets underwent rigorous quality control through a structured two-author review process. Two authors independently evaluated every sample using a standardized protocol that defined inclusion criteria (security-relevant commits with confirmed CVE identifiers, function-level line modifications, and extractable vulnerable-patched pairs), exclusion criteria (cosmetic refactoring, formatting-only changes, test modifications, and commits lacking substantiated security relevance), and required evidence documentation (CVE/CWE identifiers, commit metadata, and security rationale). Each reviewer assigned decision labels (Keep, Exclude, Requires-Discussion) with documented reasoning codes to ensure traceability and reproducibility. Inter-reviewer agreement was measured using Cohen's kappa, and all disagreements were resolved through consensus sessions with explicit rationale recording. Systematic denoising removed samples and touched functions/files that were not security-related, eliminating non-functional changes while preserving essential contextual elements necessary for semantic correctness. We removed singleton CWEs (vulnerabilities appearing only once) to ensure statistical reliability and prevent overrepresentation of rare, potentially outlier cases that could skew model evaluation. Additionally, we stripped all code comments from both vulnerable and patched code blocks to eliminate potential biases that could arise from human annotations, ensuring LLMs rely solely on code structure and semantics for VD. Deduplication removed duplicate or near-duplicate code samples (e.g., identical functions, commits, or cloned files) to prevent models from seeing the same or highly similar code during testing, employing both exact hash-based matching and token-level similarity metrics with manual inspection of flagged candidates to ensure canonical representation. Each dataset contained only one multi-label CWE vulnerability, which we retained with comprehensive annotations rather than creating duplicate entries. For LFD, we manually labeled 40 samples that lacked CWE identifiers in the NVD database, strictly adhering to NVD criteria for consistent labeling. After this comprehensive cleaning process, our final datasets comprised 314 samples in PBD and 103 samples in LFD. The fundamental approach of LLMKernelBench assembles all touched functions and non-functional elements (macros, libraries, type definitions) into cohesive vulnerable and patched code blocks that LLMs can comprehensively analyze for vulnerability prediction, ensuring complete contextual understanding rather than isolated code fragment analysis.

\textbf{CWE Distribution and Label Space.} Our dataset spans diverse CWE categories organized according to the CWE-1000 hierarchical view. Table~\ref{table:cwe-pillars} shows the distribution of vulnerabilities across the ten fundamental CWE pillars in PBD. CWE-664 dominates with 43.3\% coverage, reflecting the prevalence of memory-related vulnerabilities in the Linux kernel. The distribution also includes 12.1\% deprecated CWE identifiers (CWE-OTHER), representing historical vulnerability classifications that MITRE now marks as "PROHIBITED" for mapping. This diverse distribution ensures comprehensive evaluation across different security weakness categories, from common memory safety issues to rare configuration vulnerabilities.

\subsection{Metrics}
\label{section:metrics}

We evaluate LLM performance on VD and PV tasks using established metrics selected for their relevance to security code analysis.

\subsubsection{Label Space and Task Formulation}

\textbf{Binary labels.} For all binary VD/PV tasks (SVD3--SVD6) we use labels $y\in\{1,0\}$, where $y=1$ denotes \emph{vulnerable} code (the pre-fix version from the parent commit) and $y=0$ denotes \emph{patched} code (the post-fix version from the fixing commit). During inference we allow models to abstain with $-1$ ("not sure"); this is an optional prediction class and \emph{not} a ground-truth label.


\textbf{Why Pillar-Level Classification for LLMs?} We focus on CWE pillars rather than classes, bases, or variants because LLMs perform better when classifying into fewer, more distinct categories—with over 900 specific CWE types, fine-grained classification suffers from the curse of dimensionality and class imbalance, while the 10 pillars provide optimal granularity that is specific enough to be actionable yet broad enough for reliable pattern recognition. Pillars represent fundamentally different security principles, making them more semantically distinct for neural networks (e.g., distinguishing between "access control failures" vs. "resource management issues"), and security practitioners often think in terms of root causes rather than specific manifestations, making pillar-level classification more valuable for remediation planning. Additionally, real-world vulnerability datasets exhibit severe imbalance at fine-grained levels, with many CWE variants having fewer than 10 examples, so pillar-level aggregation provides sufficient training examples for each category, enabling more robust model training and evaluation.

\subsubsection{SVD Metrics}
For SVD tasks, we employ:
\begin{itemize}
	\item \textbf{Standard Classification Metrics}: Precision measures the ratio of correctly identified vulnerabilities to all predicted vulnerabilities. Recall quantifies the proportion of actual vulnerabilities correctly identified. F1 score provides a balanced measure between precision and recall. Accuracy represents overall correctness across all predictions.

	\item \textbf{Top-k Accuracy} \cite{russakovsky2015imagenet}: Considers a prediction correct if the true vulnerability type appears among the model's k highest-ranked predictions. We measure Top-1 to Top-5 accuracy to evaluate how well models detect and rank both CVEs and CWEs. This progressive evaluation is particularly valuable in security contexts where identifying the correct vulnerability category among top candidates enables more efficient remediation efforts, even when exact classification is challenging.

	\item \textbf{Mean Reciprocal Rank (MRR)} \cite{craswell2009mean}: Evaluates ranking quality by calculating $\frac{1}{N}\sum_{i=1}^{N}\frac{1}{\text{rank}_i}$, where $\text{rank}_i$ is the position of the correct answer in the ranked list for the $i$-th query. MRR rewards models that rank the correct vulnerability type higher, recognizing that in security contexts, prioritization of findings is crucial.

    \item \textbf{Hierarchical Proximity Score (HPS)} scores a model's outputs by how close they are to the ground-truth CWE in the hierarchy. We assign weights: exact $=1.0$, parent $=0.8$, child $=0.7$, sibling $=0.6$, same-root $=0.4$, unrelated $=0.0$. Formally, let $y_i$ be the ground truth and $(\hat y_{i1},\dots,\hat y_{ik})$ the top-$k$ predictions. Define $r(\hat y,y)\in\{\text{exact},\text{parent},\text{child},\text{sibling},\text{root},\text{none}\}$ and a weight map $w(\cdot)$ as above. The per-sample score is
    \[
      \mathrm{HPS}_i=\max_{1\le j\le k} w\big(r(\hat y_{ij},y_i)\big),
    \]
    and the dataset score is $\mathrm{HPS}=\tfrac{1}{N}\sum_{i=1}^N \mathrm{HPS}_i$. HPS credits near-misses that are semantically related, which is useful for prioritization in security triage.

\end{itemize}


\subsection{Prompt Templates}
\label{section:prompts}
Our prompt templates for VD and PV are designed with four key principles: clear task specification, structured output formats, minimal bias introduction, and scalability across vulnerability types. We focus on benchmarking inherent LLM capabilities rather than optimizing prompting strategies, evaluating baseline performance that can inform future research directions.

Each prompt clearly states the expected task and output format, uses standardized templates for fair comparison across models, maintains essential code context while avoiding information leakage, and reflects real-world security analysis scenarios. Our evaluation systematically assesses LLMs through ranking methods (SVD2) that identify the most likely vulnerability CWEs, and binary classification methods (SVD3-SVD6) that evaluate precise VD and PV capabilities.

\section{Benchmarking Results}
\label{section:results}

In this study, we leverage six pre-trained LLMs to assess their capabilities in SVD and PV tasks. Our selection comprises three code-specialized models (CodeLlama \cite{roziere2023code}, StarCoder2 \cite{lozhkov2024starcoder}, and Qwen3-Coder \cite{yang2025qwen3}) explicitly trained on programming repositories, and three general-purpose models (Llama3.1 \cite{dubey2024llama}, Mistral \cite{jiang2023mistral7b}, and DeepSeek-R1 \cite{guo2025deepseek}) designed for broader language understanding tasks. This balanced selection enables us to investigate whether domain-specific training provides advantages over general language comprehension for security-critical tasks. We selected these models based on four key criteria: (1) their state-of-the-art performance on code understanding and generation benchmarks, (2) architectural diversity spanning encoder-decoder and decoder-only designs to ensure comprehensive evaluation, (3) varying parameter sizes (7B-32B) and context window capacities (16K-262K tokens) to investigate how model scale and memory affect VD capabilities, and (4) balanced representation of code-specialized versus general-purpose training to assess domain expertise effects. While proprietary models like GPT-4 and Claude are not included in this study, the considered open-source LLMs provide sufficient evidence to demonstrate and validate the framework, which is our primary goal. \subsection{RQ1: Binary Vulnerability vs. Patch Classification}
We evaluate LLMs' ability to determine code vulnerability using precision, recall, accuracy, and F1 score metrics. Our binary classification framework assigns ground truth labels based on code state: vulnerable code blocks (pre-fix versions from parent commits) receive label 1, while patched code blocks (post-fix versions from fixing commits) receive label 0. To capture the inherent uncertainty in vulnerability assessment, we provide LLMs with a third option: -1 (meaning "not sure"). This uncertainty option is critical because: (1) real-world VD often involves ambiguous cases where even security experts disagree; (2) it prevents LLMs from making forced binary decisions when evidence is insufficient, potentially reducing false positives and negatives; (3) it provides insight into model confidence levels, enabling more nuanced evaluation of LLM reliability in security contexts; and (4) it mirrors practical security analysis workflows where analysts may need to flag code for further investigation rather than making definitive vulnerability determinations. Our analysis examines how models distinguish between these states across four prompts: SVD3 and SVD5 evaluate models on vulnerable code (expected output: 1), while SVD4 and SVD6 evaluate models on patched code (expected output: 0). SVD3/SVD4 assess non-targeted VD, while SVD5/SVD6 test targeted detection using specific CVE and CWE identifiers.

\textbf{Overall Detection Performance and Model Rankings.} Table \ref{tab:is-vulnerable} reveals striking performance hierarchies across VD tasks. CodeLlama dominates with the highest overall accuracy on both PBD (50.2\%) and LFD (53.9\%), demonstrating exceptional performance on targeted vulnerable code detection (SVD5: 92.3\% PBD, 92.2\% LFD). Mistral follows closely (48.2\% PBD, 49.8\% LFD), excelling particularly at vulnerability identification tasks (SVD3: 88.2\% PBD, 80.6\% LFD) and PV with context (SVD6: 73.9\% PBD, 82.5\% LFD). However, the performance landscape shifts dramatically across tasks: StarCoder2 leads patch detection without context (SVD4: 64.7\% PBD, 68.0\% LFD), while Llama3.1 struggles catastrophically with near-zero vulnerable code detection (0.96\% PBD SVD3, 0.0\% LFD SVD3) yet maintains moderate patch identification capabilities (42.4\% PBD SVD4), suggesting fundamental architectural weaknesses in security reasoning.

\textbf{Vulnerability vs.\ Patch Detection Asymmetry and Bias Patterns.} Models exhibit profound and systematic biases that contradict conventional security assumptions. While CodeLlama and Mistral demonstrate expected vulnerable-detection bias (CodeLlama: $+67.8$-point gap, Mistral: $+11.9$-point gap), four models show dramatic reverse bias: Qwen3-Coder ($-55.7$ points), Llama3.1 ($-44.0$ points), StarCoder2 ($-33.1$ points), and DeepSeek ($-27.7$ points). DeepSeek exemplifies this pattern, achieving only $26.3\%$ vulnerable detection versus $54.0\%$ patch detection in PBD, intensifying in LFD to $24.3\%$ versus $59.2\%$. This reverse bias challenges the assumption that models default to flagging code as vulnerable, revealing instead that many models develop sophisticated patch-recognition heuristics while failing at vulnerability identification. The cross-dataset consistency (PBD average bias: $-13.5\%$, LFD: $-20.3\%$) confirms these reflect fundamental architectural tendencies rather than training artifacts, suggesting models learn to recognize “fixed” code patterns more effectively than “broken” ones.

\textbf{CVE/CWE Context Utilization: Enhancement vs. Confusion.} 
Explicit vulnerability identifiers produce divergent effects that reveal model-specific reasoning capabilities. 
DeepSeek benefits most dramatically from targeted context, improving from 35.8\% (non-targeted) to 44.4\% (targeted) in PBD (+8.6 points) and even more substantially in LFD (+11.7 points), suggesting sophisticated vulnerability-type reasoning. 
CodeLlama shows consistent moderate gains (+3.2 points PBD, +5.8 points LFD), indicating reliable context integration. 
Conversely, Mistral and Qwen3-Coder experience performance degradation when provided CVE/CWE information (Mistral: -2.4 points both datasets; Qwen3-Coder: -3.8 points PBD), revealing that explicit vulnerability identifiers overwhelm rather than guide these models' reasoning processes. 
The overall modest positive impact (PBD: +1.3\%, LFD: +3.6\%) masks this high variance, demonstrating that effective vulnerability-type utilization remains architecture-dependent and requires specialized investigation. 
Consider CVE-2025-21762 (CWE-416 use-after-free) from LFD: the vulnerable \texttt{arp\_xmit()} function lacks RCU protection when calling \texttt{dev\_net(skb->dev)}, creating a race condition where the device structure could be freed while still in use (Figure~\ref{figure:code_2}). 
The patch adds \texttt{rcu\_read\_lock()} and \texttt{rcu\_read\_unlock()} around the critical section and switches to \texttt{dev\_net\_rcu()}. 
In this case, only \textbf{CodeLlama} correctly classified the vulnerable and patched versions across all four detection tasks (SVD3–SVD6), while every other model either misclassified the code state or responded with “not sure.” 
This results in an overall incorrectness ratio of \textbf{83.3\%} (five out of six models), confirming that most LLMs still fail the fundamental binary judgment of whether code is vulnerable or not—even when explicit contextual information and commit descriptions are provided. 
Such systematic misclassification highlights that accurate vulnerability recognition remains an unsolved capability gap rather than a prompting or dataset limitation.


\textbf{Cross-Dataset Generalization and Memory Analysis.} The PBD-to-LFD performance transitions provide definitive evidence against training data contamination while revealing temporal reasoning patterns. Remarkably, most models improve on unseen LFD data: CodeLlama ($+3.7\%$), DeepSeek ($+1.6\%$), Mistral ($+1.6\%$), and StarCoder2 ($+0.5\%$) all demonstrate positive generalization. Only Llama3.1 ($-2.8\%$) and Qwen3-Coder ($-0.9\%$) show degradation. Task-specific analysis reveals asymmetric temporal effects: vulnerable code detection declines modestly (SVD3: $-4.0\%$, SVD5: $-1.6\%$) while patch detection consistently improves (SVD4: $+3.0\%$, SVD6: $+5.1\%$). This asymmetry indicates LFD's temporal distribution (more recent vulnerabilities) better aligns with models' training data for patch patterns, while historical vulnerable code styles in PBD may be overrepresented in pretraining corpora. The combination of low absolute LFD accuracies (best: $53.9\%$) with improved relative performance definitively rules out memorization, confirming that detection capabilities reflect learned security reasoning patterns rather than training data leakage.

Our comprehensive analysis across CWE root pillars (Figures \ref{figure:cwe-distribution-PBD} and \ref{figure:cwe-distribution_LFD}) reveals dramatic specialization patterns and fundamental limitations in LLMs' security reasoning capabilities. The results expose critical insights about how different models approach various vulnerability categories and their ability to generalize across rare and common security flaws.

\textbf{Resource Control Dominance and Model Specialization.} Table~\ref{tab:cwe_pillar_performance} demonstrates that CWE-664 dominates both datasets with 136 vulnerabilities (43.3\%) in PBD and 62 (60.2\%) in LFD, representing memory-related vulnerabilities like buffer overflows, UAF, and resource leaks. CodeLlama emerges as the dominant specialist for this category, achieving exceptional performance in targeted VD (SVD5: 91.9\% in PBD, 91.9\% in LFD), while struggling significantly with PV tasks. Conversely, Mistral excels across diverse vulnerability categories, showing remarkable consistency in vulnerability identification (SVD3: 86.8\% for CWE-664, 100\% for CWE-693) but moderate PV capabilities.

\textbf{Deprecated CWE Challenge and Historical Bias.} 
The presence of 38 CWE-OTHER vulnerabilities (12.1\%) in PBD—representing deprecated identifiers like CWE-189, CWE-264, and CWE-399—creates unique challenges. 
Mistral dominates this category with 92.1\% VD accuracy, suggesting superior pattern recognition for historical vulnerability patterns that may no longer align with current security taxonomies. 
The complete absence of deprecated CWEs in LFD (0.0\%) highlights the temporal evolution of vulnerability classification and potential training data bias in models exposed to historical security databases.

\textbf{Tail Analysis and Frequency Independence.} 
Table~\ref{tab:tail} reveals remarkable findings about LLMs' generalization capabilities across vulnerability frequency distributions. 
Contrary to expectations, most models demonstrate frequency-independent performance: five of six models show excellent generalization ($\lvert r \rvert < 0.2$), with StarCoder2 achieving the most robust performance ($\Delta = +0.2\%$). 
The minimal average performance gap between short-tail (38.5\%) and long-tail (38.6\%) vulnerabilities contradicts conventional wisdom that LLMs perform better on frequent patterns. 
DeepSeek shows the strongest negative correlation ($r = -0.218$), actually performing better on rare vulnerabilities, while Mistral exhibits the only concerning frequency bias ($r = 0.122$).


\textbf{Task-Specific Vulnerability Domain Preferences.} Analysis of individual SVD tasks reveals striking domain-specific capabilities that transcend simple frequency effects. CodeLlama demonstrates exceptional targeted detection capabilities across all vulnerability types (SVD5 tasks consistently >85\%), particularly excelling with CWE-707 at 100\% accuracy in both datasets. However, this specialization comes at the cost of PV performance, where it consistently underperforms across all categories. DeepSeek shows the opposite pattern: moderate VD but superior patch identification capabilities, particularly for CWE-710 with 92.9\% accuracy in LFD.

\textbf{Dataset Distribution Effects and Temporal Patterns.} The shift from PBD to LFD reveals fundamental changes in vulnerability landscape that significantly impact model performance. LFD's increased concentration in CWE-710 from 3.5\% to 13.6\% and elimination of access control vulnerabilities (CWE-284: 8.9\% to 0.0\%) suggests evolving security practices in recent kernel development. Models show varying adaptation to these distribution shifts: Mistral maintains consistent leadership across both datasets, while others like Llama3.1 struggle universally, achieving near-zero performance in VD tasks across all categories.

These findings fundamentally challenge assumptions about LLM security capabilities, revealing that architectural differences and training methodologies create distinct vulnerability domain specializations rather than general security reasoning abilities. The frequency-independent performance suggests that current models have developed sophisticated pattern recognition for security concepts that transcends simple statistical frequency, though this capability remains highly architecture-dependent and task-specific.

\subsection{RQ4: Effect of Code Abstraction Level}

Our comprehensive analysis of six state-of-the-art LLMs across three abstraction levels reveals surprising patterns that challenge conventional assumptions about VD complexity. We evaluated both Primary Benchmark Dataset (PBD) and Leakage-Free Dataset (LFD) to ensure robust findings.

\textbf{Abstraction Does Not Always Hinder Performance.} Contrary to expectations, increasing code abstraction from single functions to multiple files does not universally degrade LLM performance. Statistical analysis shows no significant difference between abstraction levels in either dataset (PBD: p=0.8559, LFD: p=0.4259), with mean accuracies remaining remarkably stable: Level 1 (49.4\%), Level 2 (48.7\%), and Level 3 (48.8\%) in PBD.

\textbf{Model Architecture Matters More Than Size.} Our robustness analysis in Table~\ref{tab:robustness} reveals that model specialization and architecture significantly impact abstraction sensitivity. In PBD, Codellama emerges as the most robust model with performance actually \textit{improving} by 2.6\% from Level 1 to Level 3, while Starcoder shows the highest degradation at 5.1\%. Surprisingly, general-purpose models (0.5\% avg degradation) slightly outperform code-specialized models (0.6\% avg degradation).

\textbf{Context Window Size Shows Weak Correlation.} We find no significant correlation between context window size and robustness (PBD: r=0.678, p=0.322; LFD: r=-0.530, p=0.470).

\textbf{Task-Specific Patterns Emerge.} Table~\ref{tab:task_performance} demonstrates that different SVD tasks exhibit distinct sensitivity patterns. VD (SVD3) actually improves with abstraction (L1→L3: -6.1\% degradation in PBD), while patch detection (SVD4) remains stable (1.0\% degradation). This suggests LLMs benefit from additional context when identifying vulnerabilities but maintain consistent performance in distinguishing patches.

\textbf{Leakage-Free Results Show Greater Variance.} The LFD analysis reveals more dramatic performance differences, with degradation ranging from -6.9\% (Deepseek improvement) to 22.0\% (Codellama degradation). This higher variance (std=8.61 vs 3.01 in PBD) indicates that data leakage may have artificially stabilized performance metrics in traditional benchmarks.

\textbf{Key Implications for VD Systems.} Our findings fundamentally challenge the assumption that increased code abstraction universally hinders LLM performance. The lack of statistical significance across abstraction levels, combined with task-specific improvements, suggests that LLMs can effectively leverage additional context when properly trained. The superior performance of general-purpose models over code-specialized ones in abstraction robustness indicates that broad language understanding may be more valuable than domain-specific training for handling complex code structures. Most importantly, the dramatic variance in leakage-free results highlights the critical need for rigorous evaluation methodologies that avoid data contamination, as traditional benchmarks may significantly overestimate model capabilities in real-world deployment scenarios.

\section{Discussion}
\label{section:discussion}

\textbf{Key Findings.} Our benchmarking exposes fundamental limitations in LLMs' security reasoning. The low CWE detection accuracy (best: 11.4\% Top-5) and systematic bias toward memory-safety vulnerabilities reveal surface-level pattern recognition rather than deep security understanding. The reverse bias—where models detect patched code 13.5\% better than vulnerable code—contradicts assumptions about security-conscious defaults. Performance degradation with explicit CVE/CWE context suggests additional information overwhelms rather than guides reasoning. These findings indicate LLMs should serve as assistive tools under expert supervision, not autonomous analyzers, requiring significant architectural improvements for reliable vulnerability identification.

\textbf{Future Directions.} LLMKernelBench enables several research paths: (1) analyzing LLMs' reasoning processes to identify security comprehension weaknesses \cite{xiang2025towards, zibaeirad2025reasoning}; (2) expanding to multiple languages (Python, Java, Rust, Go) to assess cross-language transfer; (3) investigating hybrid LLM-agent architectures integrating static/dynamic analysis tools; (4) examining whether LLMs introduce vulnerabilities when generating patches. These directions aim to transform our diagnostic framework into a catalyst for developing robust, security-aware models.


\section{Threats to Validity}
\label{section:threatstovalidity}

\textbf{Internal Validity.}
We set temperature to 0 for all experiments to ensure deterministic outputs and reproducible results. Our benchmark evaluates fundamental VD capabilities using standardized zero-shot prompts rather than optimized prompt engineering, establishing baseline performance for future research. To prevent data contamination, we curated LFD exclusively from vulnerabilities disclosed in 2025. Since this date is after the models' training cutoffs, their inclusion in the training corpora is highly unlikely. The two-author manual review with Cohen's kappa measurement and consensus resolution ensures label quality and reduces annotation bias.
All tasks are static code reasoning (no compilation). Snippets may be non-compilable and can include function bodies or non-function edits (e.g., macros, configuration gates, header guards); we include only edits judged security-relevant. We do not reconstruct full build systems (includes, Make/Kconfig).\\
\textbf{External Validity.}
While focused on Linux kernel C code, our evaluation spans six diverse models (three code-specialized, three general-purpose) with varying architectures and parameter sizes, revealing consistent patterns across model types. The kernel's complexity and widespread use in security-critical systems make it representative of real-world vulnerability detection challenges. Performance trends observed—memory-safety bias, reverse detection bias, context degradation—likely generalize to similar systems programming contexts.\\

\section{Conclusion}
\label{section:conclusion}
This paper presents LLMKernelBench, a rigorous benchmark for evaluating LLM capabilities in vulnerability detection and patch verification using 417 real-world Linux kernel vulnerabilities. Our systematic evaluation of six state-of-the-art models reveals critical limitations: surprisingly low CWE detection accuracy (11.4\% Top-5), systematic bias toward memory-safety vulnerabilities, unexpected reverse bias favoring patch over vulnerability detection (13.5\% gap), and performance degradation with explicit security context. These findings challenge assumptions about LLMs' security reasoning and demonstrate that current models require expert supervision rather than autonomous deployment. LLMKernelBench establishes a standardized foundation for advancing LLM-based security tools through reproducible evaluation and identification of specific capability gaps requiring architectural innovation.

\section{CWE Hierarchy Example}
\label{appendix:cwe-hierarchy}

This appendix illustrates how the CWE hierarchical taxonomy enables graduated assessment of LLM security knowledge, demonstrating why our Hierarchical Proximity Score (HPS) metric provides more nuanced evaluation than exact-match accuracy alone.

\subsection{Hierarchical Structure}

The CWE hierarchy organizes vulnerabilities across four abstraction levels:
\begin{itemize}
    \item \textbf{Pillar}: Highest-level category (e.g., CWE-664: Improper Control of Resource Lifetime)
    \item \textbf{Class}: Broader weakness category (e.g., CWE-119: Improper Restriction of Operations within Memory Buffer Bounds)
    \item \textbf{Base}: Specific vulnerability type (e.g., CWE-787: Out-of-bounds Write)
    \item \textbf{Variant}: Implementation-specific manifestation (e.g., CWE-120: Buffer Copy without Checking Size of Input)
\end{itemize}

\subsection{Example: Buffer Overflow Vulnerability}

Consider CVE-2022-26490, a buffer overflow vulnerability in the Linux kernel's NFC driver (Figure~\ref{figure:cwe_example_appendix}). The vulnerable code performs an unchecked \texttt{memcpy} operation with user-controlled length, while the patched version adds bounds checking.

\begin{figure}[ht]
\centering
\includegraphics[width=0.9\columnwidth]{figures/code_1.png}
\caption{CVE-2022-26490 (CWE-120): Buffer overflow in NFC driver. The vulnerable code (top) uses user-controlled length without validation; the patch (bottom) adds bounds checking.}
\label{figure:cwe_example_appendix}
\end{figure}

An LLM analyzing this vulnerability might predict different hierarchy levels:
\begin{itemize}
    \item \textbf{Exact match} (CWE-120: Buffer Copy without Checking Size) $\rightarrow$ HPS = 1.0
    \item \textbf{Parent} (CWE-787: Out-of-bounds Write) $\rightarrow$ HPS = 0.8
    \item \textbf{Grandparent} (CWE-119: Memory Buffer Bounds) $\rightarrow$ HPS = 0.7
    \item \textbf{Root pillar} (CWE-664: Resource Lifetime) $\rightarrow$ HPS = 0.4
    \item \textbf{Unrelated} (CWE-284: Access Control) $\rightarrow$ HPS = 0.0
\end{itemize}

\subsection{Interpretation}

This graduated scoring reveals security reasoning depth: an LLM predicting CWE-119 instead of CWE-120 still demonstrates valuable understanding by recognizing the broader memory safety issue, even if lacking precision about the specific buffer operation. This approach mirrors how security experts reason—starting with broad categories before drilling down to specifics—enabling more nuanced assessment of LLMs' security knowledge, from surface-level pattern recognition to fundamental understanding of vulnerability root causes.
